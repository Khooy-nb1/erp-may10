# P0 — Discovery and Decisions

## Objective

Lock down database facts and business policies before building modules. P0 does not build business UI; it produces decisions that become contracts for P1–P10.

## P0.1 — Schema and seed inventory

### Work

- Compare schema.sql with the actual PostgreSQL database.
- Confirm database name, host, port, user, and secret management.
- Confirm the in-scope tables:
  nguoi_dung, khach_hang, san_pham, don_vi_tinh, don_ban_hang, chi_tiet_don_ban_hang, giao_hang, kho, hoa_don_ban_hang, cong_no.
- Record primary keys, foreign keys, unique keys, check constraints, string-based status values, and existing indexes.
- Load the seed into a separate development database; never seed production.
- Verify that seed rows link correctly across customers, orders, deliveries, invoices, and receivables.
- Record every real field that differs from the master plan.

### Deliverables

- docs/database/table-usage.md
- docs/database/schema-gaps.md
- A reproducible seed checklist and local command.

### Acceptance

- The database can be reached using .env.example.
- One SELECT query per scoped table succeeds.
- No business task depends on an unverified column name.

## P0.2 — Cross-module ownership

## P0.3 — Business policy

The following are decision gates; do not guess:

1. Is tax fixed, configurable, or entered per invoice?
2. May Sales override product prices?
3. Is exceeding the credit limit a warning or a hard block?
4. May one order have multiple invoices?
5. When may an invoice be created: after confirmation, after delivery, or both?
6. Who may confirm and cancel an order?
7. May a confirmed order be cancelled?
8. Does MVP delivery support line-level quantities or whole-order delivery only?
9. Is exact delivery-line history required?
10. Is payment transaction history required?

### Deliverables

- docs/decisions/business-rules.md
- docs/decisions/open-questions.md for questions without an owner.

## P0.4 — Shared API and data conventions

Agree before creating endpoints:

- Base path: /api/v1.
- Success response: success, data, message, meta.
- Error response: success, data, error.code, error.message, error.details.
- Pagination: page, pageSize, total, totalPages; cap pageSize at 100.
- Dates: ISO 8601 over the API, rendered in the business timezone.
- Money: decimal-safe backend calculations; no floating point for authoritative values.
- Business codes: generated by the backend and unique; never use COUNT(*) + 1.
- Status values: keep database values in the domain; map only display labels in the UI.

### Deliverables

- docs/api/conventions.md
- docs/api/error-codes.md
- docs/database/business-rules.md

- conditions;
- next state;
- HTTP error when rejected.

### Deliverables

## P0.6 — Technical baseline

- Record the Node, package manager, and PostgreSQL versions.
- Run syntax/build checks to identify pre-existing failures.
- Record that the current backend and frontend do not yet have a complete runtime.
- Record user changes already present; do not reset or overwrite them.

## P0 exit criteria

- Schema and seed have been checked against a development database.
- Ownership has been confirmed by the responsible owners.
- No business decision blocks P1 or P2.
- API conventions, error codes, permission matrix, and state matrix exist.
- Reproducible baseline and health-check commands are documented.
